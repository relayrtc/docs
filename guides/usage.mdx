## Imports

```ts
import { RelayServer } from '@relayrtc/node'

const relay = new RelayServer({
  apiUrl: process.env.RELAYRTC_API_URL!,
  apiKey: process.env.RELAYRTC_SECRET_KEY!,
})
```

## Fetch usage

Your secret API key needs `usage:read`.

```ts
const usage = await relay.usage.get({
  range: '7d',
  category: 'participants',
  granularity: 'day',
})

console.log(usage.summary.participantMinutesDerived)
```

Or use [GET /v1/usage](/reference/api/v1/usage/all) directly.

## Participant minutes

`participantMinutesDerived` is participant seconds divided by 60. It is a decimal quantity. A value of `5.538` means about 5.5 participant minutes, not 5,538 minutes.

Two people in a room for 5 minutes account for about 10 participant minutes.

## Time windows

Ranges are `24h`, `7d`, `14d` and `30d`. You can instead supply both `startedAt` and `endedAt`, for a positive window no longer than 30 days.

Windows use UTC. The end boundary is exclusive. Buckets align to UTC calendar hours or days and are clipped at the requested edges.

## Media and traffic

Audio, video and screen durations reflect observed active publication intervals. Paused publications and disconnected send transports do not accrue active-media duration. Microphone and screen audio overlap counts once per participant for audio; camera and screen video overlap counts once per participant for video. Screen duration is also reported separately. Screen traffic is a breakdown of SFU traffic, so do not add it to SFU totals again. Connected participant minutes are a separate measure and continue while a participant remains connected, including when media is muted. Traffic values use bytes. TURN traffic can be unavailable, partial or authoritative.

Check `dataQuality` before interpreting missing or partial usage as zero. The response’s `metricDefinitions` supplies each metric’s unit, source and aggregation.

## Scope

A key reads usage from its own project environment. Supplying another project or environment does not expand access.

## Streaming and assets (unreleased)

The unified journal requires the Phase 7 API and database migration. `GET /v1/usage` adds `serviceUsage` alongside the existing room metrics. Use `GET /v1/usage/streaming` for this report directly. The Node SDK's published usage category union may not yet include `streaming`; use REST until the matching SDK release is available.

```ts
const response = await fetch(`${process.env.RELAYRTC_API_URL}/usage/streaming?range=7d`, {
  headers: { Authorization: `Bearer ${process.env.RELAYRTC_SECRET_KEY}` },
})
if (!response.ok) throw new Error('Usage request failed')
const { serviceUsage } = await response.json()

console.log(serviceUsage.summary.liveDeliveryBytes)
console.log(serviceUsage.coverage.liveDeliveryBytes)
console.log(serviceUsage.metricDefinitions.liveDeliveryBytes)
```

| Category | What is measured |
| --- | --- |
| Sources | Encoded media progress, compositor frames, external ingress, room export and encoder program hops. |
| Outputs | Successful output time, reserved capacity, external output bytes and live transcode-profile wall time. |
| Viewers | Completed live origin response bytes, estimated recent media-request activity and peak overlap. |
| Recordings and clips | Attempted finalization, successful finalizations, completed delivery, retained bytes and storage byte-seconds. |
| DVR | Window delivery and one shared physical buffer owner, regardless of pins. |
| Mixers | Render attempts, healthy applied program, fresh input activity and submitted frames. |
| External sources | Upstream fetched bytes and worker processing. |

These are usage quantities, with `pricing: 'unpriced'`. They do not define plan allowances or introduce automatic charges. Each metric includes its unit, source and aggregation in `metricDefinitions`. Storage byte-seconds represent bytes multiplied by retained seconds; the console displays them as GiB-hours. Stored bytes are a gauge at the end of the selected window.

Durations are clipped to each UTC bucket. Byte and frame events belong to their occurrence time. Viewer peaks are recomputed for the whole scope, rather than added across resources or projects. `live` analytics means the last 15 minutes, so totals can decrease when older activity leaves the window.

### Delivery and audience coverage

Completed origin response-body bytes include manifests, successful retries and actual byte ranges. HEAD, rejected access, invalid ranges and error bodies do not become media delivery. Incomplete responses use separate partial `abortedDeliveryBytes`; bytes handed to the server transport do not prove client receipt. Durable partial intents identify responses whose completion could not be confirmed.

A playback grant alone adds no viewer time. Successful media responses establish activity; successive completions within 30 seconds create an estimated interval. The first response and longer idle gaps add no duration. Downloads and thumbnails do not create playback activity. This is not proven watch time or a count of unique people. Shared grants share an identity, and renewed grants start another identity. CDN delivery that bypasses the origin is not measured by this journal.

Inspect `coverage`, `journalStartedAt` and `historicalCoverage`. Earlier activity cannot be reconstructed from lifetime counters. An unavailable zero is not proof of no consumption. Recording and clip usage remains after retirement; expired media remains inaccessible.

Requests older than the retained service-history boundary return `USAGE_HISTORY_EXPIRED`. Select a supported window rather than interpreting expired history as zero. Open object records remain available for storage accounting within that window.

SFU, TURN, room export, upstream fetch, encoder program and external output are separate service hops. They may carry the same payload and must not be summed as unique traffic.

### Resource drilldowns

Use the same window for a project report and its resource report:

```bash
curl "$RELAYRTC_API_URL/recordings/recording_example/usage-report?range=24h" \
  -H "Authorization: Bearer $RELAYRTC_SECRET_KEY"
```

`usage-report` is available under `streams/{id}`, `broadcasts/{id}`, `recordings/{id}`, `clips/{id}`, `dvr-windows/{id}`, `mixers/{id}` and `restream-sources/{id}`. These routes require `usage:read`. They accept `24h`, `7d`, `14d`, `30d` or rolling `live`, or explicit `startedAt` and `endedAt` boundaries, and optional hour/day granularity. A stream report includes its child resources; a DVR window includes delivery and its shared physical buffer owner. Resource drilldown lists are capped at 100, with `resourcesTruncated`; scope totals include all resources.

## Streaming source usage (unreleased)

`GET /v1/streams/{id}/usage` and `relay.streams.getUsage(id)` expose observed sourceSeconds, ingressBytes, programBytes, samples and observed/partial coverage. These source-side observations remain distinct from RTC participant minutes, destination egress and HLS audience/CDN billing. Missing observations are partial coverage, not proven zero traffic. Historical usage survives stream retirement. See [streams REST](/reference/api/v1/streams).

Phase 1 [broadcast detail](/reference/api/v1/broadcasts) adds observed runSeconds/outputSeconds and separately accounted reservationSeconds. Waiting and retry gaps are excluded from live duration. Samples deduplicate by job/fence/sequence; atomic retained totals avoid rescanning the observation ledger. Missing live observations mark partial coverage. These operational units do not introduce a new billing product or infer viewer traffic.


## Multistream output observations
Phase 2 run detail distinguishes canonical HLS runSeconds from summed outputSeconds. It adds observed outbound bytes and transcodeSeconds; the latter is live output wall time under a transcoding profile, not CPU-seconds. Per-output bitrate and dropped frames are diagnostic observations. Job/fence/sequence identities deduplicate samples across attempts; missing observations remain partial. These operational measurements do not establish new viewer billing.
